# 业务汇报材料驱动的框架升级方案

更新时间：2026-04-17

## 1. 背景

本方案基于以下 4 份业务汇报材料整理：

- `C:\Project\HotelAgent\report\2024年资管财务审计部工作汇报（2025.1.23）谢总(1).pdf`
- `C:\Project\HotelAgent\report\2025年1-6月国际品牌酒店经营表现（0717）(1).pdf`
- `C:\Project\HotelAgent\report\资管中心汇报 - 2025年一季度汇报FIN(2).pdf`
- `C:\Project\HotelAgent\report\资管中心汇报 - 汇报.pdf`

这些材料和当前系统对比后，结论非常明确：

- 当前系统已经具备“自然语言问答 + 真实数据查询 + 报告式表达”的基础能力。
- 但系统主框架仍然偏向“指标问答引擎”，还不是“管理层经营分析系统”。
- 业务汇报材料体现的真实需求，是按管理层经营汇报逻辑进行结构化分析，而不是只回答某一个指标。

因此，后续优化重点不应只放在新增词表、补几个 skill 或微调提示词，而应把系统主框架升级为“经营分析编排框架”。

## 2. 问题定义

结合业务 PPT 和当前代码架构，当前系统存在 6 个核心问题。

### 2.1 主链路过于指标中心

当前主链路仍以：

```text
query -> metric -> SQL -> explanation
```

为核心，这使系统更适合回答：

- 单酒店收入怎么样
- 哪些酒店利润未达预算
- 为什么某酒店经营利润下降

但不适合回答：

- 公司所有酒店 3 月经营情况
- 请汇总到管理公司和区域维度输出
- 国际品牌和万达管理在各区域的经营差异

### 2.2 语义层更像参数提取器，不像分析规划器

当前语义层能识别：

- 时间
- 酒店
- 区域
- 品牌
- 指标
- 对比口径

但还不够擅长判断：

- 这到底是单店问题、组合问题、集团问题还是汇报问题
- 应先做组合汇总，还是先做酒店明细
- 用户要求的“管理公司和区域维度输出”是不是分组指令
- “经营情况”默认应带哪些指标包和章节结构

### 2.3 输出结构没有与管理汇报模板对齐

业务 PPT 的默认结构通常是：

1. 总体概况
2. 分组合对比
3. 分区域对比
4. 关键指标矩阵
5. 重点酒店或异常名单
6. 管理措施或经营观察

而当前系统更常见的输出结构是：

1. 某个指标的差额
2. 几家拉动酒店
3. 几家拖累酒店
4. 简短经营解释

这会导致“数据未必错，但回答层级不对”。

### 2.4 维度图谱仍不够强

PPT 中反复出现的业务维度包括：

- 管理公司
- 品牌 / 子品牌
- 国际-原万达 / 国际-自建 / 万达品牌
- 区域
- 城市等级
- 资产包
- 酒店梯队
- 科目上下级

当前系统已经开始建设维度层，但距离真正可用于管理层经营分析，还有明显差距。

### 2.5 缺少“默认报告模板选择”

当前系统已经有 skill、模板和解释服务，但还没有一层明确的 Planner 来决定：

- 本次该走哪类报告模板
- 要按哪些维度分组
- 首屏该返回什么
- 哪些深度分析需要异步补充

### 2.6 前端仍有“聊天工具感”强于“经营简报感”的问题

移动端前端已经比之前明显收敛，但离业务汇报 PPT 的阅读节奏还有差距：

- 管理层更需要“总览卡 + 分组对比 + 关键指标 + 重点名单”
- 不需要看到太多技术术语、调试信息和重复解释

## 3. 业务 PPT 给出的真实产品信号

这 4 份业务材料说明，管理层真实关注的不是“查数本身”，而是以下 5 类经营分析动作。

### 3.1 集团整体经营总览

高频口径包括：

- 总收入
- NOP / 经营利润
- NOP 率
- 维修储备金
- 含储备金 NOP
- 预算、去年同期、2023、2019 对比

### 3.2 组合经营对比

高频组合包括：

- 万达品牌
- 国际品牌
- 国际-原万达
- 国际-自建
- 兆晞资产包
- 区域组合

### 3.3 经营效率拆解

高频主题包括：

- 收入质量：总收入、客房收入、餐饮/宴会结构
- 客房效率：ADR、OCC、RevPAR
- 利润质量：利润是否跟随收入改善
- 成本效率：人工、食材、能耗、固定成本、费用率

### 3.4 排名、梯队和异常名单

PPT 中大量使用：

- 总收入前十
- RevPAR 前十
- NOP 前十
- NOP 梯队
- 亏损酒店
- 预算完成差的酒店
- 成本异常酒店

### 3.5 管理层汇报语言

汇报表达更偏：

- 量价关系
- 收入结构
- 利润转化
- 成本占收比
- 重点区域拉动
- 某组合承压
- 某区域是标杆

而不是只说“高于预算”“低于预算”。

## 4. 推荐方案

### 4.1 主框架从“问答链路”升级为“经营分析编排链路”

从：

```text
用户问题 -> 指标识别 -> SQL -> 解释
```

升级为：

```text
用户问题 -> 场景识别 -> 分析规划 -> 分组取数 -> 分层分析 -> 管理层表达
```

推荐新增的主职责层如下：

1. `Conversation Layer`
   负责对话、连续追问、上下文继承和移动端交互节奏。

2. `Semantic Graph Layer`
   负责实体识别、业务维度关系、别名体系和集合展开。

3. `Planner Layer`
   负责问题归类、模板选择、分组维度、执行顺序和首屏/深度路径拆分。

4. `Query Layer`
   负责本地仓、MySQL、外部 Provider 的多路查询与并行聚合。

5. `Analysis + Narrative Layer`
   负责经营拆解、排序、梯队、异常识别和管理层表达。

### 4.2 把“问题类型”升级为一等公民

建议 Planner 先判断问题属于哪一类，而不是先猜指标：

- `single_hotel_overview`
- `portfolio_overview`
- `company_management_report`
- `group_by_dimension_report`
- `ranking_request`
- `anomaly_scan`
- `follow_up_refinement`

其中，类似：

- “请分析一下公司所有酒店 3 月份的经营情况”
- “请汇总到管理公司和区域维度输出”

应直接命中：

- `company_management_report`
- `group_by_dimension_report`

而不是退回到单指标解释。

### 4.3 把“分组维度”纳入 query plan，而不是留给解释层猜

建议 query plan 新增显式字段：

```json
{
  "analysis_mode": "company_management_report",
  "primary_group_by": ["manage_corp", "area"],
  "secondary_group_by": ["brand", "hotel_name"],
  "themes": [
    "income_quality",
    "room_efficiency",
    "profit_quality",
    "cost_efficiency"
  ],
  "rankings": [
    "top_revenue",
    "top_revpar",
    "bottom_profit"
  ]
}
```

这样后端才能真正按“管理公司 x 区域”输出，而不是查完以后再尝试解释。

### 4.4 把 PPT 中的固定汇报结构沉淀为报告模板

建议建立 `report_templates.yaml`，至少覆盖以下模板：

- `company_overview_report`
- `manage_corp_area_report`
- `brand_comparison_report`
- `regional_overview_report`
- `single_hotel_report`
- `ranking_and_ladder_report`
- `exception_report`

每个模板都定义：

- 默认指标包
- 默认对比口径
- 默认分组维度
- 默认排名项
- 默认输出章节

### 4.5 用“指标包”替代单指标默认值

业务 PPT 告诉我们，“经营情况”不是一个指标，而是一组指标包。

建议引入 `metric_bundle` 概念：

- `operation_bundle`
  - 总收入
  - GOP / NOP
  - GOP 率 / NOP 率
  - 含储备金利润

- `room_efficiency_bundle`
  - ADR
  - OCC
  - RevPAR

- `income_structure_bundle`
  - 客房收入
  - 餐饮收入
  - 宴会收入
  - 其他收入

- `cost_efficiency_bundle`
  - 人工
  - 食材
  - 能耗
  - 固定成本
  - 运营管理成本

### 4.6 把“对比口径”和“经营口径”做成明确可见的中文配置

PPT 中的默认对比远比当前复杂，后续建议支持：

- 去年同期
- 预算
- 2023
- 2019
- 当月 / 累计
- 实际 / 预测

前端和结果中统一用中文显示，例如：

- `对比口径：去年同期`
- `经营口径：经营利润（GOP）`
- `经营口径：业主利润（经营净利润）`

### 4.7 把“酒店异常”降级为后半段，不再抢首屏

对于集团管理层问题，首屏更适合是：

1. 总体概况
2. 管理公司对比
3. 区域对比
4. 关键经营矩阵

再往下才是：

5. 重点酒店
6. 拖累酒店
7. 梯队
8. 异常名单

这会更贴近业务汇报材料的阅读方式。

### 4.8 前端要从“聊天页”继续往“移动经营简报页”演进

建议结果卡固定成：

1. 一句话经营总览
2. 关键指标条
3. 组合对比卡
4. 分层分析块
5. 重点名单
6. 你可以继续问

其中：

- 调试信息默认隐藏
- 继续追问默认收起
- 角色不同仅调整可见内容，不改变主阅读节奏

## 5. 边界与风险

### 5.1 不应让大模型直接替代事实计算

模型可以参与：

- 问题类型判断
- 模板选择
- 分组维度理解
- 经营表达

模型不应直接负责：

- 聚合值计算
- 酒店数量事实
- 自由生成未返回的数据

### 5.2 不应把所有问题都升级成重型多 Agent 流程

单店标准问题仍应保留快路径：

- 规则 + 维度图谱 + 本地仓查询 + 模板表达

只有集团汇报类、复杂组合类、跨维度对比类问题，才进入 Planner 深路径。

### 5.3 报告模板不能写死成唯一话术

模板应该规范结构，不应该锁死表达。否则系统会重新回到“看起来像 rule engine”的僵硬状态。

### 5.4 外部行业对标要明确是增强项

外部数据必须：

- 标注来源
- 标注时效
- 明确与内部数据口径未必完全一致

不应与内部财务事实混在一起输出。

## 6. 实施建议

### 6.1 P0：把管理层问题先答对

目标：先解决“问得像汇报，答得像问答”的错位问题。

开发重点：

- 新增 `company_management_report` 和 `group_by_dimension_report`
- query plan 增加 `group_by_dimensions`
- 输出支持 `管理公司`、`区域`、`管理公司 x 区域`
- 默认首屏从“酒店异常”切到“组合对比”

### 6.2 P1：把报告模板和指标包体系建立起来

开发重点：

- 建立 `report_templates.yaml`
- 建立 `metric_bundles.yaml`
- 扩展维度图谱：管理公司、资产包、品牌层级、科目层级
- 增加排序、梯队和异常扫描查询模块

### 6.3 P2：引入 Planner + Semantic Graph 主导的新链路

开发重点：

- Planner 统一做问题分类和执行计划
- Semantic Graph 统一做实体和关系解析
- Skill 从主链路退到辅助能力
- 报告类问题按模板驱动而不是按触发词驱动

### 6.4 P3：多 Agent 与学习闭环

开发重点：

- Analysis Agent 负责经营拆解
- Narrative Agent 负责管理层表达
- Learning Agent 负责失败样本和追问沉淀
- 外部行业对标作为异步增强

## 7. 当前进展

截至当前分支，已经具备的基础包括：

- 真实 MySQL + 本地 DuckDB 双层数据链路
- 管理层移动端对话界面
- 组合类报告章节输出
- `公司全部酒店` 这类根范围语义识别
- 去年同期默认口径回归
- 多 Agent 演进主方案和 Skill / Harness / Hermes 方向文档

当前最需要补上的，不是继续堆规则，而是：

- 让 Planner 能真正理解“这是管理层汇报类问题”
- 让 Query Layer 真正支持“按维度汇总输出”
- 让前端把结果按业务汇报结构展示出来

一句话总结：

当前系统已经具备“经营问答助手”的底座，下一步要做的是把它升级为“经营汇报编排器”。
