# 文档规范管理

本文档用于约束本项目 `docs/` 目录的文档命名、分类、更新方式和维护要求，确保后续持续开发时文档可追踪、可复用、可交接。

## 1. 管理目标

本项目文档管理遵循四个目标：

1. 可快速定位  
   新成员进入项目后，能够迅速知道“看哪份文档、解决什么问题”。

2. 可持续更新  
   每次架构调整、链路整改、配置变化、重要验证结果，都有明确落点，不依赖口头记忆。

3. 可审计回顾  
   阶段性开发过程、关键决策、验证结果和当前边界需要可回放。

4. 可区分层级  
   总览文档、专题设计、执行记录、部署说明不能混在一起。

## 1.1 当前编号目录规则

`docs/` 根目录只保留 `README.md` 作为总入口，其余文档按编号目录归档：

- `01_OVERVIEW`：项目总览、代码架构、阶段总结。
- `02_ARCHITECTURE_EVOLUTION`：架构演进、报告模板、多 Agent、业务 PPT 驱动方案。
- `03_SEMANTIC_AND_MODEL`：语义层、模型边界、Skill / Harness / Hermes。
- `04_DATA_AND_BENCHMARK`：本地数据仓、外部行业对标。
- `05_PRODUCT_EXPERIENCE`：前端体验、ChatGPT 交互对齐、管理层移动端体验。
- `06_EXECUTION_LOGS`：阶段执行记录。
- `07_OPERATIONS_DELIVERY`：启动、部署、性能、交付和演示。
- `99_DOCUMENTATION_GOVERNANCE`：文档规范和治理规则。

新增文档时，应优先放入已有编号目录；只有出现稳定的新文档类别时，才新增编号目录，并同步更新 `docs/README.md`。

## 2. 文档分类规则

`docs/` 下文档统一分为四类：

### 2.1 总览类

用于回答“项目整体是什么、当前到哪一步”。

示例：

- `PROJECT_REVIEW_AND_ARCHITECTURE.md`
- `ARCHITECTURE_OVERVIEW.md`

要求：

- 面向管理层、交接人或新加入开发者
- 优先讲整体，不堆实现细节
- 适合作为总入口文档

### 2.2 专题设计类

用于回答“某个能力怎么设计、边界是什么、为什么这么做”。

示例：

- `HIGH_EFFICIENCY_MULTI_AGENT_ARCHITECTURE.md`
- `EXTERNAL_BENCHMARK_PROVIDER.md`
- `LLM_REASONING_BOUNDARY.md`
- `SEMANTIC_DIMENSION_LAYER.md`
- `SKILL_HARNESS_EVOLUTION_PLAN.md`

要求：

- 一个主题一份文档
- 讲清设计目标、结构、边界、后续演进
- 避免把阶段执行流水直接混进去

### 2.3 执行记录类

用于回答“这一轮具体做了什么、如何验证、结果是什么”。

示例：

- `PHASE3_EXECUTION_LOG.md`

要求：

- 一轮重大阶段推进对应一份执行记录
- 必须包含：目标、执行过程、验证方式、结果、边界、下一步建议
- 强调事实记录，不写成泛泛总结

### 2.4 运维与使用类

用于回答“如何启动、部署、调试、验证、交付”。

示例：

- `LOCAL_STARTUP.md`
- `DEPLOYMENT_NOTES.md`
- `PERFORMANCE_TUNING.md`
- `LOCAL_WAREHOUSE.md`
- `DELIVERY_CHECKLIST.md`
- `DEMO_SCRIPT.md`

要求：

- 面向实际操作
- 强调步骤、命令、环境变量、注意事项
- 保证可执行性

## 3. 命名规范

文档文件名统一使用：

- 全大写英文
- 单词之间用下划线 `_`
- 后缀统一为 `.md`

推荐格式：

- 总览类：`*_OVERVIEW.md` / `PROJECT_*.md`
- 专题设计类：`<TOPIC>.md`
- 执行记录类：`PHASE*_EXECUTION_LOG.md`
- 运维类：`LOCAL_*.md` / `*_NOTES.md` / `*_CHECKLIST.md`

禁止：

- 中英文混杂文件名
- 临时命名如 `new_doc.md`、`todo.md`、`test123.md`
- 同主题反复新建多份重复文档而不做归并

## 4. 内容结构规范

### 4.1 总览类文档结构

建议顺序：

1. 文档用途
2. 当前状态
3. 系统分层
4. 数据链路
5. 模型策略
6. 当前边界
7. 下一步方向

### 4.2 专题设计类文档结构

建议顺序：

1. 背景
2. 问题定义
3. 设计目标
4. 推荐方案
5. 边界与风险
6. 实施建议
7. 当前进展

### 4.3 执行记录类文档结构

必须包含：

1. 本轮目标
2. 执行过程
3. 代码落点
4. 验证过程
5. 结果
6. 当前边界
7. 下一步建议

### 4.4 运维类文档结构

建议顺序：

1. 适用范围
2. 前置条件
3. 操作步骤
4. 验证方式
5. 常见问题
6. 风险提示

## 5. 更新规则

后续开发时，满足以下任一条件，必须同步更新文档：

1. 新增或改变系统主链路能力  
   例如语义解析、查询规划、分析表达、学习闭环、外部 Provider。

2. 新增重要接口  
   例如系统设置接口、学习汇总接口、外部 Provider 状态接口。

3. 修改关键统计口径  
   例如“在营酒店数”的定义和数据来源。

4. 修改部署、启动、缓存、模型配置方式  
   例如新增环境变量、切换本地仓、调整服务端口。

5. 完成一个可独立回顾的开发阶段  
   需要补充阶段执行记录。

## 6. 链接管理规则

项目内文档应尽量互相建立入口关系：

- 总览文档要链接到关键专题文档
- 重大阶段执行记录要能从总览文档进入
- 专题设计文档应写明相关总览文档和执行记录文档

要求：

- 不新增“孤立文档”
- 新文档创建后，至少在一个上级入口文档中加入口

## 7. 版本与历史记录规则

本项目当前采用“主文档 + 阶段执行记录”的管理方式：

- 稳定结论写入主文档
- 过程与验证写入执行记录
- 不建议在主文档中堆叠大量流水式历史内容

当某个主题经历重大迭代时：

- 保留原专题文档继续维护
- 新增对应执行记录
- 如结论已经稳定，再把最终结论回写到主专题文档

## 8. 当前建议执行方式

后续每完成一轮较大的架构或能力推进，建议同时执行：

1. 更新一份主文档  
   记录“现在系统是什么”

2. 更新一份执行记录  
   记录“这一轮怎么做的、怎么验证的”

3. 更新总入口文档  
   让团队知道该去哪里看

## 9. 当前目录建议角色

当前 `docs/` 可按如下理解：

- `README.md`
  文档总入口和编号目录索引
- `01_OVERVIEW/PROJECT_REVIEW_AND_ARCHITECTURE.md`
  项目总入口
- `01_OVERVIEW/ARCHITECTURE_OVERVIEW.md`
  代码架构总览
- `02_ARCHITECTURE_EVOLUTION/HIGH_EFFICIENCY_MULTI_AGENT_ARCHITECTURE.md`
  多 Agent 演进主方案
- `06_EXECUTION_LOGS/PHASE3_EXECUTION_LOG.md`
  最近一轮阶段执行记录
- `04_DATA_AND_BENCHMARK/EXTERNAL_BENCHMARK_PROVIDER.md`
  外部对标专题设计
- `07_OPERATIONS_DELIVERY/LOCAL_STARTUP.md` / `07_OPERATIONS_DELIVERY/DEPLOYMENT_NOTES.md`
  启动与部署说明

## 10. 规范结论

从现在开始，本项目文档管理统一遵循：

- 先分类，再写文档
- 先有入口，再新增专题
- 先记录结果，再补过程
- 阶段执行必须有记录
- 主结论和执行流水必须分开

这样可以保证项目在持续开发、多阶段重构和多人接手时，文档仍然清晰、可维护、可审计。
