# 酒店经营 AI 助手对齐 ChatGPT 交互体验整改方案

本文档用于梳理当前酒店经营 AI 助手与 ChatGPT 式人机交互体验之间的差异，并进一步拆解为产品需求清单和开发优先级，作为后续交互整改的统一依据。

## 1. 文档目标

本项目是垂直类酒店经营分析助手，不需要变成通用聊天产品，但需要在基础交互体验上尽量向 ChatGPT 看齐。

因此本次整改目标不是“做一个通用大模型聊天壳”，而是：

- 保留酒店经营分析的垂直能力
- 提升会话体验、历史记录、上下文承接、状态反馈和用户掌控感
- 让管理层在移动端使用时，获得更接近成熟 AI 助手的交互体验

## 2. 当前差异点

### 2.1 会话能力差距

ChatGPT 的会话体验更成熟，主要体现在：

- 有明确的会话列表
- 支持回看历史
- 支持继续基于旧对话追问
- 会话边界清晰

当前酒店助手的状态更接近：

- 单条线程式经营问答页面
- 消息虽然连续显示，但没有真正的会话管理层
- 用户很难回到“上次分析华南区经营情况”的那个上下文

### 2.2 上下文承接差距

ChatGPT 的连续追问体验很自然，用户可以直接说：

- “继续展开”
- “只看华南区”
- “那换成同比”

当前酒店助手虽然已经具备一定连续追问能力，但仍存在这些问题：

- 上下文承接依赖单一当前状态
- 范围、时间、口径、对象的继承不够稳定
- 用户对系统“当前按什么上下文理解”缺少足够清晰的感知

### 2.3 状态反馈差距

ChatGPT 在等待、生成、失败、重试上的反馈更自然，用户很少会感到“系统没反应”。

当前酒店助手的问题主要是：

- 问题提交后仍然偏任务执行感
- 有时用户不清楚系统到底在处理什么
- 失败时虽然已经比之前更人话，但整体感受还没有达到成熟聊天产品级别

### 2.4 历史记录差距

ChatGPT 的历史记录不只是消息堆栈，而是用户与助手持续协作的入口。

当前酒店助手还没有形成：

- 会话列表
- 最近分析记录
- 主题化归档
- 收藏问题
- 常用追问沉淀

### 2.5 用户控制感差距

ChatGPT 的一个重要体验优势是：用户大致知道模型正在理解什么。

当前酒店助手虽然已经开始展示识别范围和分析模式，但还不够系统化：

- 用户不一定知道当前问题继承了哪些历史上下文
- 用户不容易快速切换当前对话的时间、口径、对象
- 历史问题之间缺少明显隔离

## 3. 整改原则

本项目后续对齐 ChatGPT 交互体验时，遵循以下原则：

1. 垂直能力优先  
   不削弱酒店经营分析能力，不为了聊天而聊天。

2. 交互体验补齐  
   在会话、历史记录、上下文承接、状态反馈上向成熟聊天产品看齐。

3. 移动端优先  
   所有交互设计优先考虑管理层移动办公场景。

4. 对话感优先于参数感  
   用户尽量通过自然语言完成分析，而不是不断填筛选条件。

5. 用户必须有掌控感  
   系统应明确展示当前按什么范围、时间、口径和上下文在分析。

## 4. 产品需求清单

### 4.1 一级需求：会话层

目标：让系统从“单页问答”升级为“可持续对话的经营助手”。

需求清单：

1. 会话列表
   用户可以看到最近会话。

2. 新建会话
   用户可以开启一条新的分析线程，避免上下文串线。

3. 会话标题
   每条会话自动生成简短标题，支持后续人工重命名。

4. 会话切换
   用户切换到旧会话后，原消息和上下文一起恢复。

5. 历史回看
   用户可以回看曾经问过的问题与系统返回的分析结果。

6. 最近更新时间排序
   最近活跃会话优先展示。

### 4.2 一级需求：上下文层

目标：让连续追问更像与分析师协作，而不是重新输入一遍参数。

需求清单：

1. 当前会话上下文对象
   每条会话独立维护自己的范围、时间、酒店、区域、指标、口径和摘要。

2. 连续追问重写
   对“继续展开原因”“只看华南区”“换成同比”“改成经营摘要”等表达进行稳定改写。

3. 上下文提示
   在输入区或结果区提示系统当前承接的上下文。

4. 上下文隔离
   不同会话之间不能共享业务上下文。

5. 当前问题理解提示
   当系统对追问做了重写时，明确展示“已按上下文理解为：...”

6. 轻量纠偏
   当上下文不明确时，优先轻量确认，而不是直接误解。

### 4.3 二级需求：历史与记忆层

目标：让系统逐步成为管理层自己的经营分析工作台。

需求清单：

1. 最近会话
2. 收藏问题
3. 常用追问
4. 最近查看酒店 / 区域 / 品牌
5. 按主题归档历史分析

### 4.4 二级需求：状态反馈层

目标：让用户始终知道系统现在在做什么。

需求清单：

1. 发送后立即进入明确状态
2. 分阶段提示：已理解 / 查数据 / 生成分析 / 准备追问
3. 失败时给出可理解原因
4. 支持重试
5. 保留技术诊断，但默认弱化

### 4.5 二级需求：结果层

目标：让首屏结果像管理层产品，而不是调试输出。

需求清单：

1. 首屏只看经营观察
2. 结构化明细默认折叠
3. 继续追问默认折叠
4. 支持一键切换分析方式
5. 每轮结果后给出自然的下一步问题

## 5. 开发优先级

### P0：必须优先完成

这部分直接决定系统是否具备接近 ChatGPT 的基础交互体验。

1. 会话列表
2. 新建会话
3. 会话切换与历史恢复
4. 会话级上下文隔离
5. 连续追问稳定承接
6. 当前上下文提示

### P1：应尽快完成

这部分决定系统是否足够顺手、是否像成熟 AI 助手。

1. 会话自动命名
2. 会话重命名
3. 最近会话排序
4. 结果后推荐追问优化
5. 状态反馈与失败提示继续细化

### P2：中期增强

这部分决定系统是否从“好用”进一步走向“可长期使用”。

1. 收藏问题
2. 常用追问沉淀
3. 最近查看酒店 / 区域 / 品牌
4. 主题化历史归档
5. 个性化管理层工作台入口

## 6. 建议的实施顺序

### 第一阶段：会话基础设施

实现：

- 会话数据结构
- 会话列表
- 新建会话
- 切换会话
- 本地持久化

目标：

先让系统真正从单线程聊天页，升级成多会话助手。

### 第二阶段：上下文承接升级

实现：

- 会话级 `ConversationContext`
- 范围 / 时间 / 口径 / 指标 / 对象的稳定继承
- 连续追问重写增强
- 上下文提示条

目标：

让“继续展开原因”“只看华南区”“换成同比”变得稳定自然。

### 第三阶段：历史体验增强

实现：

- 自动标题
- 重命名
- 历史回看
- 最近会话排序

目标：

让用户下次打开时，感觉是在继续工作，而不是重新开始。

### 第四阶段：记忆与工作台增强

实现：

- 收藏问题
- 常用追问
- 最近查看对象
- 主题归档

目标：

让系统逐步成为管理层自己的经营分析工作台。

## 7. 对当前项目的直接建议

根据当前项目状态，建议先做下面两项：

1. 会话列表与会话级历史管理
2. 会话级上下文承接与上下文提示

原因是：

- 这是与 ChatGPT 体验差距最大的两个点
- 也是连续追问、历史回看、移动端使用体验的基础
- 不依赖后端大改，优先可以在前端先落地最小可用版本

## 8. 验收标准

当下面这些场景都成立时，可以认为基础交互体验开始接近 ChatGPT：

1. 用户可以创建多条经营分析会话。
2. 用户切回旧会话时，消息和上下文都恢复。
3. 用户说“继续展开原因”，系统能稳定继承上一问。
4. 用户说“只看华南区”“换成同比”，系统能稳定承接。
5. 用户能清楚看到系统当前按什么上下文在分析。
6. 用户不会因为开启新问题而污染旧会话。

## 9. 当前结论

酒店经营 AI 助手不需要变成通用 ChatGPT，但需要具备接近 ChatGPT 的基础人机交互能力。

后续整改方向应当是：

- 内核继续强化酒店经营分析
- 外壳在会话、上下文、历史、反馈体验上向成熟聊天产品看齐

当前最值得优先推进的，就是：

1. 会话列表与历史管理
2. 会话级上下文承接能力
