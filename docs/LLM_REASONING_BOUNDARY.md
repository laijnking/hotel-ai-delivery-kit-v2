# 大模型推理边界与介入策略

## 1. 核心结论

本项目需要大模型的推理能力，但不应该把大模型放在每次查询的必经路径里。

更合理的方式是：

```text
规则 / 维度图谱负责确定性识别，
大模型负责不确定场景的推理、消歧和分析表达。
```

也就是说，大模型应该是副驾驶和分析专家，而不是基础维度识别的唯一入口。

## 2. 为什么不能全部依赖大模型

酒店经营问答里有大量确定性信息，例如：

- 区域：华南区、华东区、海南区。
- 酒店：江门嘉华、广州丽思卡尔顿酒店。
- 管理公司：万达品牌、国际品牌。
- 品牌 / 子品牌：嘉华、万豪、希尔顿、凯悦。
- 部门：客房部、餐饮部、管理部门、固定成本。
- 科目：收入、成本、酒水成本、营业毛利、经营净利润。
- 时间：202603、3月、本月、去年同期。

这些信息在数据库基础表、维度表、科目树或实体目录中都有明确来源。如果每次都交给大模型判断，会带来几个问题：

- 响应变慢，移动端体验会变差。
- 结果不稳定，同一句话可能被模型拆成不同参数。
- 审计困难，无法解释为什么某个字段被映射成某个维度。
- 成本增加，高频管理查询会反复调用模型。
- 空结果更难定位，不清楚是模型误判、SQL 问题还是数据不存在。

因此，确定性维度识别应该优先走规则、实体目录、别名表、科目树和维度图谱。

## 3. 大模型适合介入的场景

### 3.1 低置信语义解析

当规则层无法稳定判断用户意图时，可以调用快模型进行结构化补位。

示例：

```text
看一下高端酒店的经营情况
```

这里“高端酒店”可能对应：

- `brand_level in ['奢华级', '豪华五星级', '标准五星级']`
- 或用户只是泛指表现较好的酒店
- 或用户想看高房价、高 RevPAR 酒店

这类表达需要模型结合字段含义和上下文提出候选解释。

### 3.2 多候选消歧

当一个词可能对应多个维度时，大模型可以帮助判断或生成追问。

示例：

```text
看万豪3月收入情况
```

“万豪”可能是：

- 子品牌 / 品牌体系
- 某些酒店名称中的词
- 管理口径下的一类酒店

系统可以先用实体图谱查候选，再由模型判断是否足够明确。若不明确，前端追问：

```text
你这里的“万豪”是指品牌/子品牌，还是包含万豪字样的单酒店？
```

### 3.3 口径冲突判断

当用户同时给出互相冲突的维度时，大模型可以帮助识别冲突并触发澄清。

示例：

```text
看华南区的北京万丽经营情况
```

如果维度图谱显示北京万丽不属于华南区，系统不应该直接查空，而应该提示：

```text
我识别到“华南区”和“北京万丽”可能不在同一范围内。你想以区域为准，还是以酒店为准？
```

### 3.4 复杂经营分析表达

当数据已经查出后，大模型适合做分析表达，例如：

- 层层拆解收入质量、客房效率、利润质量、成本效率。
- 按同区域、同品牌、同档次做横向对标。
- 生成经营摘要、报告、复盘材料。
- 将结构化数据转成管理层更容易理解的自然语言。

但这里必须有边界：

```text
大模型只能基于已返回数据进行分析，不能自行编造事实、行业行情或经营结论。
```

## 4. 推荐的分层架构

### 4.1 第一层：规则与维度图谱

职责：

- 识别确定性实体。
- 识别时间、指标、对比口径。
- 识别酒店、区域、管理公司、品牌、子品牌、档次、城市等级。
- 识别 P&L 部门和科目层级。
- 根据维度图谱判断从属关系。

特点：

- 快。
- 稳定。
- 可审计。
- 可测试。

### 4.2 第二层：快模型消歧

职责：

- 处理规则低置信问题。
- 将模糊表达映射成候选维度。
- 判断是否需要追问。
- 输出结构化 JSON，而不是直接生成最终答案。

模型建议：

```text
qwen3.5-flash
```

输出建议：

```json
{
  "intent": "query",
  "metric_code": "TOTAL_INCOME",
  "requested_areas": [],
  "requested_hotels": [],
  "requested_manage_corps": [],
  "requested_brand_children": ["万豪"],
  "requested_brand_levels": [],
  "requested_departments": [],
  "requested_accounts": [],
  "confidence": 0.78,
  "needs_clarification": false,
  "reasoning_note": "用户提到万豪，更可能是品牌/子品牌口径。"
}
```

### 4.3 第三层：深度模型分析

职责：

- 在数据返回后做专业经营分析。
- 生成摘要、报告、横向对标说明。
- 帮助用户连续追问。

模型建议：

```text
qwen3.6-plus
```

约束：

- 输入必须包含查询结果。
- 输出必须引用已返回数据。
- 缺少数据时必须说明“当前数据不足”。
- 不直接做未经数据支持的好坏判断。

### 4.4 第四层：学习闭环

职责：

- 收集低置信解析样本。
- 收集空结果样本。
- 收集用户改问和追问样本。
- 由 Harness 定期沉淀别名、规则、Skill 和评测用例。

沉淀对象：

- 新酒店别名。
- 新品牌别名。
- 科目同义词。
- 管理公司别名。
- 常见问法模板。
- 新的业务 Skill。

## 5. 当前项目推荐策略

### 5.1 普通移动端经营查询

```powershell
$env:QWEN_PARSE_POLICY="auto"
$env:QWEN_EXPLANATION_POLICY="off"
```

说明：

- 高置信规则解析直接返回。
- 低置信或需要澄清时调用快模型。
- 解释默认使用本地结构化模板，保证速度。

### 5.2 深度经营分析 / 报告

```powershell
$env:QWEN_PARSE_POLICY="auto"
$env:QWEN_EXPLANATION_POLICY="auto"
```

说明：

- 解析仍然优先规则和图谱。
- 报告、归因、深度分析场景调用深度模型增强表达。

### 5.3 模型调优验证阶段

```powershell
$env:QWEN_PARSE_POLICY="always"
$env:QWEN_EXPLANATION_POLICY="always"
```

说明：

- 适合观察模型能力和收集样本。
- 不建议作为管理层移动端默认体验。

## 6. 判断是否调用大模型的建议规则

可以按以下条件判断：

- 规则置信度高于阈值，例如 `0.82`：不调用模型。
- 识别到明确酒店、月份、指标、维度：不调用模型。
- 只有泛化词，例如“高端酒店”“核心酒店”“表现差的酒店”：调用快模型。
- 出现多个候选维度：调用快模型或追问。
- 维度从属关系冲突：追问优先。
- 用户要求“原因、归因、报告、总结、对标”：可调用深度模型。
- 查询结果为空：记录学习样本，并判断是否需要模型协助生成澄清问题。

## 7. 对 Skill / Harness / Hermes 的意义

### Skill

Skill 应该沉淀稳定业务能力，例如：

- 单酒店经营概览。
- 多酒店对比。
- 区域经营摘要。
- 品牌经营对标。
- P&L 科目归因。

Skill 中应声明：

- 触发词。
- 默认指标。
- 必要维度。
- SQL 口径。
- 输出结构。

### Harness

Harness 应该负责持续评测：

- 问法是否被正确解析。
- 维度是否命中。
- SQL 是否过滤正确。
- 回答是否引用了正确数据。
- 低置信样本是否被沉淀成新规则。

### Hermes

Hermes / Agent 编排更适合用于复杂任务：

- 多步骤分析。
- 横向对标。
- 自动生成报告。
- 多数据源联动。
- 异常样本回放和调优建议。

但 Hermes 不应该替代基础确定性解析层。否则系统会重新变成黑箱。

## 8. 最终原则

本项目的大模型使用原则是：

```text
能由数据库和维度图谱确定的，不交给模型猜。
需要语义推理和消歧的，让快模型结构化判断。
需要专业表达和复杂分析的，让深度模型在数据约束下生成。
所有低置信、空结果、用户修正都进入学习闭环。
```

这样可以同时获得：

- 响应速度。
- 结果稳定性。
- 业务解释能力。
- 可审计性。
- 持续自学习能力。
